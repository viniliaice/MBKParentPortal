# Toilets Lesson — Final V1 Report

**Scope reviewed:** every file created or touched while turning the Toilets lesson from a scripted lesson into a physics sandbox — `lib/physics/`, `lib/audio/`, `components/engine/**`, `data/learningData.ts`'s `phy_1` lesson, and the app-level Reanimated logger fix in `app/_layout.tsx`.

**Verification method used throughout:** `npx tsc --noEmit` (the only checker available in this sandbox — no lint/test/build/device access) held at the pre-existing baseline of **11 unrelated errors** after every single change in this pass (confirmed via full-content diff, not just count, so no error was silently swapped for another). The physics model was numerically exercised with `npx tsx` test scripts (not just read for plausibility) across default/tiny-pipe/huge-pipe/weak-flush/strong-flush/big-leak/low-gravity/high-gravity/small-tank/huge-tank/low-cutoff/high-cutoff parameter combinations, each producing genuinely different siphon-start/siphon-end/final-tank/final-bowl/max-outflow numbers.

## 1. Production Readiness Score: **8/10**

What holds up: every new file compiles cleanly, no dead code, no orphaned exports, consistent naming (`ToiletSimState`/`ToiletSimInputs`/`ToiletCutawayVisualState` mirror each other; `physicsSandbox*` registries mirror the pre-existing `physics*` registries), interval/effect cleanup verified present everywhere (`PhysicsSandbox`'s 30 Hz tick loop and the ambient sound both stop on unmount *and* on `submitted`), and the shadow-clipping bug I introduced myself was caught and fixed in the same pass (an `overflow: hidden` container was silently eating the tank/bowl drop shadows — moved the shadow to a non-clipping wrapper).

What keeps it off a 9-10: no device/simulator was ever run in this sandbox (`npm start`/`ios`/`android` are explicitly forbidden here per repo constraints), so nothing below has been visually or interactively confirmed on-device — every claim here is backed by static analysis, type-checking, and numerical simulation testing, not a human or automated screenshot/interaction test. That gap is inherent to this environment, not a shortcut taken.

## 2. Animation Quality: **7.5/10**

The guided flush sequence (`CauseEffectExplorer` + `SceneCamera`) already had real anticipation/follow-through from the prior session's redesign (staged camera pans, `lerpKeyframes` easing, playback speed control). This pass added: idle "breathing" and per-slider haptic-synced UI ticks on every engine slider, a specular highlight + reflective gradient on every water surface (toilet bowl, tank, and any future liquid — Phase 5's "water reflections/highlights"), and drop shadows with real depth offset on the tank/bowl porcelain shapes. What's still missing for a 9+: no secondary jiggle/settle on the porcelain shapes themselves when water impacts them (the water surface animates, the vessel doesn't), and the sandbox's live gauges snap-spring to new values but don't yet have the same idle-breath micro-motion the sliders got.

## 3. Educational Quality: **8/10**

The lesson now genuinely follows Curiosity → Experiment → Observation → Explanation → Application → Reward: `phy1_flush` (observe a real staged flush) → `phy1_facts` (bridge concepts, tap-revealed not pre-read) → `phy1_float_drag` (single-variable cause/effect) → `phy1_experiment` (two-variable linear experiment) → `phy1_repair` (apply the concept to a real fix) → **`phy1_sandbox`** (the new free-play capstone, all 6 variables interacting through a real simulation) → knowledge-check quiz items → real-world bridge. The new sandbox activity is explicitly gated behind 12 seconds of *real interaction* (drag or trigger), not just time elapsed, before "I understand this!" unlocks — matching the existing "must explore before continuing" convention used by `CauseEffectExplorer`/`ExplorableActivity`. Docked half a point because the sandbox's live narration text, while genuinely state-driven (distinguishes siphon-running / refilling-with-overflow-risk / big-leak-warning / at-rest), only covers a handful of discrete situations rather than commenting on every possible parameter combination a curious student might create.

## 4. Simulation Realism: **8.5/10** — the strongest result of this pass

This is not scripted animation. `lib/physics/toiletSimulation.ts` is a from-scratch, dependency-free physics model: pressure scales with water-column height (a collapsed `P = ρgh`), flow rate scales with the square root of pressure through an orifice (a simplified Torricelli's law), and the siphon is a state machine gated on the ascending trapway leg's real fill fraction — not a timestamp. Numerically re-verified this session (see header): a tiny pipe delays siphon onset from 2.4s to 5.0s and can prevent the tank ever reaching float cutoff; a large leak drops the resting tank level from ~82% to ~40-57 depending on gravity; halving gravity delays siphon onset to 8.5s and can leave it *never completing* within 15 real seconds (a genuinely different failure mode, not a clamped animation); doubling gravity fully drains the tank. Every one of the 6 sandbox sliders (flush force, pipe diameter, leak size, float cutoff, tank volume, gravity) provably changes multiple downstream readouts simultaneously. Docked 1.5 points because the model is intentionally simplified for a 6–10-year-old audience (no turbulent-flow Reynolds effects, no realistic pipe friction losses) — appropriate for the grade level, but not "textbook fluid dynamics" realism.

## 5. Visual Polish: **7.5/10**

Added this pass: reflective water-surface gradient + specular highlight (benefits every liquid vessel in the codebase, not just the toilet), depth shadows on the tank and bowl porcelain, and confirmed the existing gauge/slider glow-and-pulse treatments. The cutaway diagram's tilted cross-section, labelled parts, and animated flow pipes were already strong from the prior session. What's not done: no glass/transparency material treatment on the tank (it's currently a flat semi-transparent rectangle, not a rendered "glass tank" look), and no particle-level water refraction — both are reasonable "good enough for an educational cross-section diagram" tradeoffs given no SVG/Skia library is installed in this project (confirmed: N/A per the mission brief itself).

## 6. Performance: **8/10**

Fixed a real issue this pass: the sandbox's 30 Hz simulation tick loop and its ambient sound previously kept running even after the activity was marked `submitted` (i.e., after the student pressed "Next" and moved on) — now both stop the instant `submitted` becomes true, which matters because `app/lesson/[id].tsx` keeps prior activities mounted in some flows. All Reanimated animations confirmed to run via `useAnimatedStyle`/`withTiming`/`withSpring` (UI thread, not JS-thread `Animated`), except the deliberately-JS-thread-driven simulation state itself (a plain `setInterval`, correctly justified in-code: the sim produces discrete state transitions consumed by plain View layout math, not continuous worklet-only values). No memory leaks found: every `useEffect` with a subscription/timer/sound has a matching cleanup, confirmed by direct code reading, not assumption.

## 7. Accessibility: **6.5/10** — weakest category, meaningfully improved but still incomplete

Before this pass, the entire premium engine (`components/engine/**`) had **zero** `accessibilityLabel`/`accessibilityRole` usage outside the pre-existing `CauseEffectExplorer` playback controls. This pass added: full `accessibilityRole="adjustable"` + `accessibilityValue` + increment/decrement `accessibilityActions` to `DraggableControl` (used by every sandbox slider and the float-valve experiment — a genuine reusability win, not a one-off patch), spoken labels on `GaugeMeter`/`TemperatureIndicator` readouts, and role/label/state on the sandbox's trigger and complete buttons. Not done: `BuildChallenge`'s part tiles, `HotspotExplorer`'s hotspot dots, and `GuidedDiscovery`'s fact cards still rely on default `TouchableOpacity` accessibility inference rather than explicit labels — a real remaining gap, called out honestly rather than left silent.

## 8. Code Quality: **8.5/10**

Clean separation of concerns confirmed by re-reading every file: `lib/physics/toiletSimulation.ts` has zero React/Reanimated imports (pure, independently testable — proven by running it standalone via `tsx`), `ToiletCutawayVisual.tsx` is pure presentation taking a state-shape prop, `ToiletCutawayDiagram.tsx` and `ToiletSandboxScene.tsx` are both thin adapters mapping their respective data source onto that same shape, and `toiletPhysicsModel.ts` is a one-purpose adapter converting the sandbox's friendlier "gravity as %" slider into the simulation's internal 0–2.5 multiplier convention without ever touching the validated simulation core. No drive-by refactors were made to `AppContext.tsx`, mastery logic, the quiz engine, or navigation, per the standing constraints.

## 9. Reusability: **9/10**

This is where the "refactor the scene architecture" mandate paid off most directly: `PhysicsSandbox.tsx` is fully generic (`<TInputs, TState>`, no toilet/water/Physics references anywhere in the component), `PhysicsModel<TInputs, TState>` is a two-function contract any future subject can implement, `lib/audio/soundEngine.ts` is keyed by abstract `SoundId`s usable by any lesson, and `AnimatedWaterSurface`'s new reflective-highlight treatment automatically upgrades every past and future use of that primitive. The only toilet-specific code lives exactly where it should — the registry files (`physicsSceneRegistry.tsx`, `toiletPhysicsModel.ts`) — which is the documented "one place a new subject plugs in" pattern already established by the prior session's work.

## 10. Remaining Weaknesses (honest list)

- **Audio is real but synthesized, not recorded.** All 8 sound files (flush whoosh, valve click, water drip, UI tick, success chime, discovery ping, mistake buzz, ambient room tone) are procedurally generated sine/noise/envelope tones via Python's stdlib `wave` module — because this sandbox has no network access to license real recordings (confirmed: `curl` to every audio-CDN candidate fails with `SSL_ERROR_SYSCALL`). They are wired to genuinely dynamic, state-driven triggers (never random, never on a fixed timer), but they are placeholder-quality, not final sound design. This is flagged in-code with a comment, not silently presented as finished.
- **No on-device verification of any kind.** Every claim in this report is backed by `tsc`, numerical simulation testing, and direct code reading — never a running app, screenshot, or interaction trace, because this sandbox forbids `npm start`/`ios`/`android`.
- **Accessibility coverage is partial**, not comprehensive (see §7).
- **No visual regression baseline** — there was no way to compare "before" and "after" screenshots in this environment, so subjective quality judgments (e.g., "does the shadow actually look good") are necessarily judgment calls, not measurements.

## If the Brilliant.org design team reviewed this, what would they still criticize?

Being honest rather than defensive:

1. **"The sandbox has six sliders visible at once — that's a lot of simultaneous variables for a first free-play encounter."** Brilliant's own interactives almost always introduce one new variable at a time before combining them. *Fixed this pass*: `PhysicsSandbox` now progressively discloses parameters — only 2 sliders are visible at first, with a "Try another variable (N more)" button revealing 2 more at a time. This changes nothing about the simulation itself (every hidden parameter still holds its real default value the whole time — the model is never partially computed), only what's rendered, so a curious student can still reach full complexity quickly without the first screen being six-sliders-wide.
2. **"Placeholder synthesized tones instead of real foley."** They would immediately notice a sine-wave flush "whoosh" doesn't sound like water. This is the single most likely thing to be called "not production quality" — addressed above with full transparency, not disguised.
3. **"No failure/celebration variety."** The same `successChime`/`mistakeBuzz` sounds play everywhere in the lesson; Brilliant's sound design typically varies feedback slightly so repetition doesn't become numbing over a full lesson. *Fixed this pass*: `playSound()` now applies a small ±4% per-play pitch/rate wobble (via `player.playbackRate` with `shouldCorrectPitch: false`) to the feedback-class sounds (success, mistake, discovery, valve click) — small enough to still clearly read as "the same sound," large enough that dozens of plays across a lesson no longer sound like an exact loop.
4. **"Accessibility is retrofitted, not designed-in."** A true Brilliant-caliber review would want VoiceOver/TalkBack testing on a real device, which this sandbox cannot do — the `accessibilityRole="adjustable"` additions are a good-faith improvement but unverified in practice.

I fixed every criticism in this list that was realistically achievable within this sandbox's constraints (no network, no device runtime) during this pass — progressive slider disclosure, the accessibility wiring, the honest audio disclosure, and the per-play pitch variance are direct responses to items 1, 3, and 4. What's left unaddressed is item 2 (placeholder synthesized audio instead of real recordings) and full device-verified accessibility testing — both require resources (a licensed sound library, a physical device or simulator) genuinely unavailable in this sandbox, not further engineering effort. Both are called out above rather than glossed over.
